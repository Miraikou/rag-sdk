# 核心接口定义

> 本文档定义了 RAG SDK 所有模块的抽象接口。所有代码严格遵循 TypeScript strict 模式，禁止使用 `any`。

---

## 1. 全局基础类型

### 1.1 Document（文档）

**用途：** 表示一个原始文档，是 Pipeline 摄入阶段的最小单元。`metadata` 使用 `Record<string, unknown>` 而非 `any`，确保类型安全的同时支持任意扩展字段。

```ts
interface Document {
  id: string;
  content: string;
  metadata: Record<string, unknown>;
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `string` | 全局唯一标识符，由 Loader 生成 |
| `content` | `string` | 文档原始文本内容 |
| `metadata` | `Record<string, unknown>` | 可扩展元数据（来源、标题、时间等） |

### 1.2 Chunk（文本块）

**用途：** 表示文档切块后的片段，是检索与生成的核心单元。`parentId` / `children` 支持 Small-to-Big 检索策略——先检索小粒度 chunk，再回溯父 chunk 获取完整上下文；`contextHeader` 支持 Contextual Chunk Header 增强策略。

```ts
interface Chunk {
  id: string;
  documentId: string;
  content: string;
  metadata: Record<string, unknown>;
  embedding?: number[];
  parentId?: string;
  children?: string[];
  contextHeader?: string;
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `string` | chunk 全局唯一标识 |
| `documentId` | `string` | 所属文档 ID |
| `content` | `string` | 切块后的文本内容 |
| `metadata` | `Record<string, unknown>` | chunk 级元数据（位置、序号等） |
| `embedding` | `number[]` \| `undefined` | 向量表示，由 EmbeddingProvider 填充 |
| `parentId` | `string` \| `undefined` | 父 chunk ID（Small-to-Big 场景） |
| `children` | `string[]` \| `undefined` | 子 chunk ID 列表 |
| `contextHeader` | `string` \| `undefined` | 上下文头信息（Contextual Chunk Header） |

### 1.3 SearchResult（检索结果）

**用途：** 统一封装检索结果，`source` 字段标识来源通道，便于混合检索（Hybrid Search）场景下的结果融合与调试。

```ts
type SearchSource = 'vector' | 'keyword' | 'graph' | 'fusion';

interface SearchResult {
  chunk: Chunk;
  score: number;
  source: SearchSource;
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `chunk` | `Chunk` | 命中的文本块 |
| `score` | `number` | 相关性分数（0~1 归一化） |
| `source` | `SearchSource` | 检索来源通道 |

### 1.4 Citation（引用）

**用途：** 答案生成时附带的引用信息，用于溯源和可解释性。与 Chunk 的区别在于 Citation 是面向最终用户展示的轻量结构。

```ts
interface Citation {
  chunkId: string;
  documentId: string;
  content: string;
  metadata: Record<string, unknown>;
}
```

### 1.5 GenerateResult（生成结果）

**用途：** 封装 LLM 生成阶段的完整输出，包含答案文本、引用来源和额外元数据（如 token 消耗、延迟等）。

```ts
interface GenerateResult {
  answer: string;
  sources: Citation[];
  metadata: Record<string, unknown>;
}
```

### 1.6 Message（消息）

**用途：** LLM 对话的标准消息格式，遵循主流 LLM API 的 role/content 约定。

```ts
type MessageRole = 'system' | 'user' | 'assistant';

interface Message {
  role: MessageRole;
  content: string;
}
```

## 2. LLMProvider — LLM 提供商接口

**用途：** 抽象大语言模型的调用方式，屏蔽不同厂商（OpenAI、Anthropic、本地模型等）的差异。提供同步和流式两种调用模式。

```ts
interface ChatOptions {
  model?: string;
  temperature?: number;
  maxTokens?: number;
  topP?: number;
  stop?: string[];
}

interface LLMProvider {
  /**
   * 同步调用 LLM，返回完整回复文本。
   * @param messages - 对话消息列表
   * @param options - 可选的生成参数
   */
  chat(messages: Message[], options?: ChatOptions): Promise<string>;

  /**
   * 流式调用 LLM，逐步返回文本片段。
   * 适用于实时展示生成过程的场景。
   * @param messages - 对话消息列表
   * @param options - 可选的生成参数
   */
  chatStream(messages: Message[], options?: ChatOptions): AsyncIterable<string>;
}
```

### 方法说明

| 方法 | 说明 |
|------|------|
| `chat` | 一次性返回完整回复。适合非交互场景（批量评估、后台处理） |
| `chatStream` | 以 `AsyncIterable` 逐 token/chunk 返回。适合对话 UI 实时渲染 |

### ChatOptions 参数

| 参数 | 类型 | 说明 |
|------|------|------|
| `model` | `string` | 模型标识（如 `gpt-4o`、`claude-3-sonnet`） |
| `temperature` | `number` | 采样温度，0~2，越低越确定 |
| `maxTokens` | `number` | 最大输出 token 数 |
| `topP` | `number` | 核采样概率 |
| `stop` | `string[]` | 停止生成的标记序列 |

### 设计考量

- 使用 `AsyncIterable<string>` 而非回调或 Event，契合现代 JS 异步迭代协议，消费端可用 `for await...of` 自然消费。
- `ChatOptions` 所有字段可选，避免强制传入默认值；具体 Provider 实现内部维护默认配置。
- 不暴露模型厂商特有参数（如 `frequency_penalty`），通过 `ChatOptions` 保持通用性；如需扩展，具体实现可提供子类接口。

## 3. EmbeddingProvider — 向量嵌入接口

**用途：** 抽象文本到向量的映射能力。支持单条和批量嵌入，`dimension` 属性让上游（VectorStore 初始化）能动态感知向量维度。

```ts
interface EmbeddingProvider {
  /**
   * 将单条文本转为向量表示。
   * @param text - 输入文本
   * @returns 浮点数向量
   */
  embed(text: string): Promise<number[]>;

  /**
   * 批量将多条文本转为向量，实现可优化网络请求（批处理）。
   * @param texts - 输入文本数组
   * @returns 与输入顺序一致的向量数组
   */
  embedBatch(texts: string[]): Promise<number[][]>;

  /**
   * 当前模型的向量维度（如 OpenAI text-embedding-3-small 为 1536）。
   * VectorStore 初始化时依赖此值构建索引。
   */
  readonly dimension: number;
}
```

### 方法说明

| 方法 | 说明 |
|------|------|
| `embed` | 单条文本嵌入，适合实时查询场景 |
| `embedBatch` | 批量嵌入，Pipeline 摄入阶段使用，实现应利用批处理 API 降低成本 |
| `dimension` | 只读属性，标识向量维度，便于 VectorStore 动态建索引 |

### 设计考量

- `embedBatch` 独立于 `embed`，允许实现端做请求合并（如 OpenAI 单次最多 2048 条），而非简单循环调用 `embed`。
- `dimension` 作为实例属性而非方法参数，因为维度由模型决定、在 Provider 生命周期内不变。

## 4. VectorStore — 向量存储接口

**用途：** 抽象向量数据库的 CRUD 与检索操作。`upsertByDocument` / `deleteByDocument` 支持按文档粒度的增量更新，避免全量重建索引。

```ts
interface SearchOptions {
  topK?: number;
  filter?: Record<string, unknown>;
  threshold?: number;
}

interface VectorStore {
  /**
   * 插入或更新 chunk 及其向量。
   * @param chunks - 待写入的 chunk 列表（需包含 embedding）
   */
  upsert(chunks: Chunk[]): Promise<void>;

  /**
   * 按文档 ID 批量写入 chunk，用于增量更新场景。
   * 实现应保证同一文档 ID 下的旧数据被替换。
   * @param documentId - 文档 ID
   * @param chunks - 该文档切块后的 chunk 列表
   */
  upsertByDocument(documentId: string, chunks: Chunk[]): Promise<void>;

  /**
   * 向量相似度检索。
   * @param query - 查询向量
   * @param options - 检索选项
   */
  search(query: number[], options?: SearchOptions): Promise<SearchResult[]>;

  /**
   * 按 chunk ID 删除。
   * @param ids - 待删除的 chunk ID 列表
   */
  delete(ids: string[]): Promise<void>;

  /**
   * 按文档 ID 删除其所有 chunk。
   * @param documentId - 文档 ID
   */
  deleteByDocument(documentId: string): Promise<void>;
}
```

### SearchOptions 参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `topK` | `number` | `5` | 返回的最大结果数 |
| `filter` | `Record<string, unknown>` | `undefined` | 基于 metadata 的过滤条件 |
| `threshold` | `number` | `0` | 最低相关性阈值，低于此分数的结果被过滤 |

### 设计考量

- `upsertByDocument` 独立于通用 `upsert`，因为按文档增量更新是 RAG 系统的常见运维需求，部分向量数据库（如 Pinecone）原生支持 namespace 级别的批量操作。
- `filter` 使用 `Record<string, unknown>` 而非强类型，因为 metadata 结构因业务而异；具体实现可在此基础上增加过滤语法（如 Pinecone 的 filter expression）。
- 不在接口层定义连接/初始化方法，这些由具体实现（构造函数或工厂方法）处理。

## 5. Chunker — 切块策略接口

**用途：** 抽象文档切块逻辑。不同切块策略（固定大小、递归、语义、上下文头）均实现此接口，Pipeline 可按需替换。

```ts
interface ChunkOptions {
  chunkSize?: number;
  overlap?: number;
  separator?: string;
}

interface Chunker {
  /**
   * 将文档切分为 chunk 列表。
   * @param document - 待切分的文档
   * @param options - 切块参数
   * @returns chunk 列表（不含 embedding，由后续阶段填充）
   */
  chunk(document: Document, options?: ChunkOptions): Chunk[];
}
```

### ChunkOptions 参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `chunkSize` | `number` | `500` | 目标 chunk 大小（字符数或 token 数） |
| `overlap` | `number` | `50` | 相邻 chunk 的重叠大小，保证上下文连续性 |
| `separator` | `string` | `'\n'` | 优先使用的切分分隔符 |

### 设计考量

- `chunk` 方法返回 `Chunk[]` 而非 `Promise<Chunk[]>`，因为纯文本切块本身是同步操作。对于需要异步依赖（如 SemanticChunker 依赖 Embedding）的场景，实现可返回同步结果，embedding 由 Pipeline 统一填充——或扩展为 `Promise<Chunk[]>`（具体实现中可覆盖签名）。
- 保持接口极简，复杂策略的特有参数（如 `similarityThreshold`）在具体实现的构造函数中注入。

## 6. DocumentLoader — 文档加载器接口

**用途：** 抽象不同格式文档的加载逻辑。每种文件格式（txt、md、pdf、json、csv、网页）对应一个实现类。

```ts
interface DocumentLoader {
  /**
   * 从文件路径、URL 或 Buffer 加载文档。
   * @param source - 文件路径（string）或二进制内容（Buffer）
   * @returns 文档列表（一个文件可能拆分为多个 Document，如 PDF 按页拆分）
   */
  load(source: string | Buffer): Promise<Document[]>;
}
```

### 设计考量

- `source` 接受 `string | Buffer`：string 用于文件路径或 URL，Buffer 用于已在内存中的二进制内容（如上传文件）。
- 返回 `Document[]` 而非单个 `Document`：某些格式天然产生多个文档（PDF 每页一个、CSV 每行一个）。
- 不包含 `canLoad(source)` 类型判断方法——由调用方或工厂函数负责路由到正确的 Loader。

---

## 7. QueryTransformer — 查询变换接口

**用途：** 在检索前对用户查询进行变换，提升检索质量。典型策略包括查询改写（Rewrite）、查询扩展（Expansion / HyDE）、子问题分解（Sub-Questions）。

```ts
interface QueryTransformer {
  /**
   * 对原始查询进行变换。
   * @param query - 用户原始查询
   * @returns 变换后的单条查询或多条查询（多查询场景下 Retriever 需对每条分别检索后合并）
   */
  transform(query: string): Promise<string | string[]>;
}
```

### 设计考量

- 返回 `string | string[]` 而非固定数组：单查询改写（如 Rewriting）返回 `string`，多查询扩展（如 Multi-Query、Sub-Questions）返回 `string[]`。
- 异步接口：大多数变换策略需要调用 LLM（如 HyDE 生成假设性答案），天然异步。
- Pipeline 中可配置多个 QueryTransformer，按顺序链式执行。

---

## 8. Retriever — 检索器接口

**用途：** 抽象检索逻辑，将"查询 → 相关 chunk 列表"的过程封装为统一接口。不同检索策略（向量检索、关键词检索、混合检索、图检索）均实现此接口。

```ts
interface RetrieveOptions {
  topK?: number;
  filter?: Record<string, unknown>;
}

interface Retriever {
  /**
   * 根据查询检索相关 chunk。
   * @param query - 查询文本（已经过 QueryTransformer 处理）
   * @param options - 检索选项
   * @returns 按相关性排序的检索结果列表
   */
  retrieve(query: string, options?: RetrieveOptions): Promise<SearchResult[]>;
}
```

### 设计考量

- Retriever 接收原始查询文本（`string`）而非向量（`number[]`），内部的向量化由 Retriever 自行完成——这使 Retriever 能组合多路检索（向量 + 关键词），每路使用各自的向量化或分词方式。
- 与 `VectorStore.search` 的区别：`VectorStore.search` 是底层向量操作，`Retriever` 是高层检索策略（可能组合多个 Store、加入重排、执行 RRF 融合等）。

---

## 9. PostProcessor — 后处理器接口

**用途：** 在检索结果送入 Generator 之前进行后处理。典型操作包括：重排序（Reranker）、冗余去除、最大边际相关性（MMR）、结果截断。

```ts
interface PostProcessor {
  /**
   * 对检索结果进行后处理。
   * @param results - 原始检索结果列表
   * @param query - 原始查询（部分后处理策略如 Reranker 需要查询信息）
   * @returns 处理后的结果列表（可能减少、重排序或修改分数）
   */
  process(results: SearchResult[], query: string): Promise<SearchResult[]>;
}
```

### 设计考量

- 传入 `query` 参数：Reranker 类后处理器需要 query 与 chunk 的交叉注意力来计算新的相关性分数。
- 返回 `SearchResult[]`：后处理器可以修改分数（Reranker）、过滤结果（MMR）、甚至替换 chunk 内容（Small-to-Big 中将小 chunk 替换为其父 chunk）。
- Pipeline 支持配置多个 PostProcessor，按顺序链式执行。

---

## 10. Generator — 答案生成器接口

**用途：** 封装"检索结果 + 用户查询 → 生成答案"的过程。负责 Prompt 构造、LLM 调用、引用提取。

```ts
interface GenerateOptions {
  promptTemplate?: string;
  maxTokens?: number;
  includeSources?: boolean;
}

interface Generator {
  /**
   * 基于检索到的 chunk 生成答案。
   * @param query - 用户查询
   * @param chunks - 检索到的相关 chunk 列表
   * @param options - 生成选项
   * @returns 包含答案、引用和元数据的完整生成结果
   */
  generate(
    query: string,
    chunks: Chunk[],
    options?: GenerateOptions
  ): Promise<GenerateResult>;
}
```

### GenerateOptions 参数

| 参数 | 类型 | 说明 |
|------|------|------|
| `promptTemplate` | `string` | 自定义 Prompt 模板，支持 `{query}` `{context}` 占位符 |
| `maxTokens` | `number` | 最大生成 token 数 |
| `includeSources` | `boolean` | 是否在结果中包含引用来源（默认 `true`） |

### 设计考量

- 传入 `Chunk[]` 而非 `SearchResult[]`：Generator 只需 chunk 内容和元数据来构造 Prompt，不需要检索分数。如需分数信息，可通过 metadata 传递。
- `promptTemplate` 支持自定义：不同业务场景可能需要不同的 Prompt 风格（如要求引用标注、限制回答范围等）。

---

## 11. Pipeline — 编排器接口

**用途：** RAG 流程的顶层编排器，串联摄入（Ingest）和查询（Query）两条完整链路。是使用者的主要交互入口。

```ts
interface Pipeline {
  /**
   * 摄入文档：加载 → 清洗 → 切块 → 嵌入 → 存储。
   * @param documents - 待摄入的文档列表
   */
  ingest(documents: Document[]): Promise<void>;

  /**
   * 查询：查询变换 → 检索 → 后处理 → 生成答案。
   * @param question - 用户问题
   * @returns 完整的生成结果（答案 + 引用）
   */
  query(question: string): Promise<GenerateResult>;

  /**
   * 流式查询：与 query 相同的流程，但以流式返回答案文本。
   * 适用于对话 UI 的实时渲染场景。
   * @param question - 用户问题
   */
  queryStream(question: string): AsyncIterable<string>;
}
```

### 设计考量

- `ingest` 和 `query` 对应 RAG 的两条核心链路，职责清晰分离。
- `queryStream` 独立于 `query`：流式场景下无法等待完整答案后再提取引用，因此流式模式通常只返回答案文本，引用信息通过其他渠道（如完成事件）传递。
- Pipeline 是接口而非类：允许不同编排策略（如带缓存的 Pipeline、支持多轮的 Pipeline）以不同方式实现。

---

## 12. PipelineConfig — Pipeline 配置

**用途：** Pipeline 的构造参数，区分必填组件和可选组件。必填组件构成最小可用 RAG 链路，可选组件用于增强检索质量。

```ts
interface PipelineConfig {
  /** LLM 提供商（必填）—— 用于 Generator 和可能的 QueryTransformer / ContextualHeaderChunker */
  llm: LLMProvider;

  /** 向量嵌入提供商（必填）—— 用于 chunk 嵌入和查询嵌入 */
  embedding: EmbeddingProvider;

  /** 向量存储（必填）—— chunk 的持久化与检索 */
  store: VectorStore;

  /** 切块策略（必填）—— 文档切分 */
  chunker: Chunker;

  /** 查询变换器链（可选）—— 按顺序执行 */
  queryTransformers?: QueryTransformer[];

  /** 自定义检索器（可选）—— 不指定时使用基于 store 的默认向量检索 */
  retriever?: Retriever;

  /** 后处理器链（可选）—— 按顺序执行 */
  postProcessors?: PostProcessor[];

  /** 自定义生成器（可选）—— 不指定时使用基于 llm 的默认生成器 */
  generator?: Generator;
}
```

### 必填 vs 可选

| 组件 | 必填 | 说明 |
|------|------|------|
| `llm` | ✅ | Generator 的核心依赖，不可或缺 |
| `embedding` | ✅ | chunk 嵌入和查询嵌入的基础 |
| `store` | ✅ | 存储和检索的基座 |
| `chunker` | ✅ | 文档切分是摄入链路的必要步骤 |
| `queryTransformers` | ❌ | 默认不做查询变换 |
| `retriever` | ❌ | 默认使用 store 自带的向量检索 |
| `postProcessors` | ❌ | 默认不做后处理 |
| `generator` | ❌ | 默认使用基于 llm 的标准生成器 |

## 13. Evaluator — 评估器接口

**用途：** 分别评估检索质量和生成质量，支持 RAG 系统的量化评估与持续优化。

### 13.1 MetricResult（指标结果）

```ts
interface MetricResult {
  /** 指标名称（如 "recall@5"、"faithfulness"） */
  name: string;

  /** 指标得分（通常 0~1） */
  score: number;

  /** 可选的详细信息（如各子维度分数、中间计算结果） */
  details?: Record<string, unknown>;
}
```

### 13.2 RetrievalEvaluator（检索评估器）

**用途：** 评估检索结果与标注答案（Ground Truth）的匹配程度。常用指标：Recall@K、MRR、NDCG。

```ts
interface RetrievalEvaluator {
  /**
   * 评估检索结果质量。
   * @param results - 系统检索结果
   * @param groundTruth - 标注的相关 chunk ID 列表
   * @returns 评估指标结果
   */
  evaluate(results: SearchResult[], groundTruth: string[]): MetricResult;
}
```

### 13.3 GenerationEvaluator（生成评估器）

**用途：** 评估生成答案的质量。常用指标：Faithfulness（忠实度）、Answer Relevancy（答案相关性）、Context Precision（上下文精确度）。

```ts
interface GenerationEvaluator {
  /**
   * 评估生成答案质量。
   * @param answer - 系统生成的答案
   * @param reference - 参考答案（人工标注）
   * @param context - 可选的上下文 chunk 列表（用于评估忠实度）
   * @returns 评估指标结果
   */
  evaluate(
    answer: string,
    reference: string,
    context?: Chunk[]
  ): MetricResult;
}
```

### 设计考量

- 检索评估和生成评估分离：RAG 系统的两条链路质量需要独立诊断，混合评估无法定位瓶颈在检索还是生成。
- `MetricResult` 统一封装：不同评估器可能产出不同指标，统一的 `name + score + details` 结构便于上层汇总和可视化。
- `details` 字段使用 `Record<string, unknown>`：不同指标的详情结构差异大（如 NDCG 需要各等级得分，Faithfulness 需要逐句判定结果），保持灵活。
