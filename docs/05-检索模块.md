# 检索模块

> 本文档描述检索模块的设计理念和模块架构。具体 API 签名和使用方式请参考对应源码文件中的 JSDoc 注释。

检索模块是 RAG 系统的核心环节，负责根据用户查询从知识库中找到最相关的内容。本模块分为三个子模块：**查询变换**、**搜索策略**、**后处理**。

---

## 一、查询变换 (Query Transformation)

查询变换的目标是在检索之前对用户的原始查询进行预处理和优化，提升检索质量。

### 1. QueryRewriter（查询重写）

#### 概念说明

将用户模糊、口语化的问题改写成更精准、更适合检索的 query。用户的提问往往包含口语化表达、指代不清、关键词缺失等问题，直接用于检索效果较差。

#### 解决的问题

- 用户输入过于模糊（如"这个东西怎么用"）
- 缺少关键术语和上下文
- 口语化表达与文档的书面化表达不匹配

> 源码详见：`packages/retrieval/src/query/rewriter.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `rewritePrompt` | `string` | 内置默认提示词 | 自定义重写提示词模板 |

#### 使用示例

```typescript
import { QueryRewriter } from '@rag-sdk/retrieval'

const rewriter = new QueryRewriter(llmProvider)

// 基础重写
const rewritten = await rewriter.transform('这个东西怎么用')
// → "XX产品 使用指南 操作步骤"

// 使用自定义提示词
const customRewriter = new QueryRewriter(llmProvider, {
  rewritePrompt: `你是技术文档检索助手。将用户问题改写为精准查询。只输出改写结果。`,
})
const result = await customRewriter.transform('怎么导出数据')
// → "数据分析模块 导出功能 CSV Excel 操作指南"
```

### 2. MultiQueryExpander（多查询变换）

#### 概念说明

将一个问题从多个不同角度改写，生成多个 query 同时检索，然后合并结果。单次检索可能因 query 表述方式不同而遗漏相关内容，多查询可以显著提升召回率。

#### 解决的问题

- 单一 query 可能遗漏不同表述方式的相关内容
- 某些内容用 A 表述能搜到，用 B 表述搜不到
- 提升整体召回率，减少信息遗漏

> 源码详见：`packages/retrieval/src/query/multi-query.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `numQueries` | `number` | `3` | 生成的查询数量，范围 3-5 |
| `temperature` | `number` | `0.7` | 生成温度，越高结果越多样 |

#### 使用示例

```typescript
import { MultiQueryExpander } from '@rag-sdk/retrieval'

const multiQuery = new MultiQueryExpander(llmProvider, {
  numQueries: 4,
  temperature: 0.8,
})

const queries = await multiQuery.transform('如何提升用户留存')
// → [
//   "提升用户留存率的方法和最佳实践",
//   "降低用户流失率的策略与手段",
//   "增加用户活跃度和粘性的运营方案",
//   "用户生命周期管理中的留存优化技巧"
// ]

// 用多个 query 分别检索，合并结果
const allResults = []
for (const q of queries) {
  const results = await vectorStore.search(q, { topK: 5 })
  allResults.push(...results)
}
```

### 3. QueryDecomposer（查询拆解）

#### 概念说明

将复杂问题拆分成多个独立的子问题，分别检索后综合回答。与 `MultiQueryExpander` 不同，`QueryDecomposer` 不是从不同角度改写同一个问题，而是把一个复合问题拆成多个真正独立的子问题。

#### 解决的问题

- 复杂问题涉及多个维度，单一 query 难以覆盖
- 拆分后的子问题更聚焦，检索更精准
- 每个子问题可以独立检索和验证

> 源码详见：`packages/retrieval/src/query/decomposition.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `maxSubQueries` | `number` | `5` | 最大子问题数量 |

#### 使用示例

```typescript
import { QueryDecomposer } from '@rag-sdk/retrieval'

const decomposer = new QueryDecomposer(llmProvider, { maxSubQueries: 4 })

const subQueries = await decomposer.transform(
  '对比 React 和 Vue 的生态系统、学习曲线、性能和适用场景',
)
// → [
//   "React 生态系统包含哪些核心库和常用工具",
//   "Vue 生态系统包含哪些核心库和常用工具",
//   "React 和 Vue 的学习曲线对比",
//   "React 和 Vue 在不同规模项目中的适用场景"
// ]

// 分别检索每个子问题
const resultsPerQuery = await Promise.all(
  subQueries.map((q) => vectorStore.search(q, { topK: 3 })),
)
```

### 4. HyDETransformer（假设文档嵌入）

#### 概念说明

HyDE（Hypothetical Document Embeddings）先让 LLM 针对用户问题生成一个假设性的答案文档，然后用这个假设文档（而非原始 query）去做向量检索。

#### 解决的问题

用户查询通常是口语化的短句（如"怎么部署到生产环境"），而知识库中的文档是正式的、详细的书面表达。两者在 Embedding 空间中的距离可能较远，导致检索效果差。通过生成假设文档，弥合了口语化 query 和正式文档之间的语义鸿沟。

> 源码详见：`packages/retrieval/src/query/hyde.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `generatePrompt` | `string` | 内置默认提示词 | 自定义生成假设文档的提示词 |

#### 使用示例

```typescript
import { HyDETransformer } from '@rag-sdk/retrieval'

const hyde = new HyDETransformer(llmProvider)

// 1. 生成假设文档
const hypotheticalDoc = await hyde.transform('如何优化数据库查询性能')
// → "优化数据库查询性能可以从多个维度入手：1. 索引优化...2. 查询语句优化...3. 缓存策略..."

// 2. 用假设文档的 Embedding 去检索（而非原始 query）
const embedding = await embeddingProvider.embed(hypotheticalDoc)
const results = await vectorStore.search(embedding, { topK: 5 })
```

### 5. RetrievalRouter（检索路由）

#### 概念说明

根据问题的类型、内容、复杂度等信息，动态决定走哪条检索路径。不同的问题适合不同的数据源和检索方式，路由机制可以实现精准的检索策略分发。

#### 解决的问题

- 不同类型的问题需要检索不同的数据源
- 不同场景适合不同的检索方式（向量、关键词、知识图谱）
- 简单问题无需复杂的多路检索，避免资源浪费

> 源码详见：`packages/core/src/router.ts`

#### 路由方式

- **规则路由**：通过正则表达式匹配关键词 → 选择合适的 Retriever
- **LLM 路由**：用 LLM 判断查询类型 → 动态选择检索策略（`RetrievalRouter.createLLMRule()`）
- **自定义路由**：用户通过 `addRule()` 注入自定义 match 函数

#### 关键类型

```typescript
// 路由决策
interface RouteDecision {
  type: string              // 路由类型标识
  retriever: Retriever     // 选中的检索器
  options?: Record<string, unknown>
}

// 路由规则
interface RouteRule {
  name: string
  match: (query: string) => boolean | Promise<boolean>
  retriever: Retriever
  options?: Record<string, unknown>
}
```

#### 使用示例

```typescript
import { RetrievalRouter } from '@rag-sdk/core'

// 定义路由规则
const rules: RouteRule[] = [
  {
    name: 'finance',
    match: (query) => /财报|营收|利润|成本|预算/.test(query),
    retriever: financeRetriever,
    options: { topK: 10 },
  },
  {
    name: 'keyword-search',
    match: (query) => /错误码|API名称|函数名/.test(query),
    retriever: keywordRetriever,
  },
  // 使用 LLM 创建的规则
  RetrievalRouter.createLLMRule(llm, 'complex', fusionRetriever, '需要多步推理的复杂问题'),
]

const router = new RetrievalRouter(defaultVectorRetriever, rules)

// 路由并执行检索
const decision = await router.route('去年第三季度的营收是多少')
// → { type: 'finance', retriever: financeRetriever }
const results = await decision.retriever.retrieve(query, decision.options)
```

## 二、搜索策略 (Search Strategies)

搜索策略定义了从知识库中查找相关内容的具体方式。不同策略有不同的优势和适用场景，所有搜索策略均实现 `Retriever` 接口（`retrieve(query, options?): Promise<SearchResult[]>`）。

### 1. VectorSearch（向量检索）

#### 概念说明

将查询文本通过 Embedding 模型转换为向量，然后在向量数据库中计算余弦相似度，找到语义最相近的文档片段。这是 RAG 系统中最基础的检索方式。

#### 解决的问题

- 语义级别的匹配，能理解同义词、近义表达
- 不依赖精确的关键词匹配
- 适合模糊查询和概念性查询

> 源码详见：`packages/retrieval/src/search/vector.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `topK` | `number` | `5` | 返回结果数量 |
| `minScore` | `number` | `0` | 最低相似度阈值 |
| `filter` | `Record<string, unknown>` | `undefined` | 元数据过滤条件 |

#### 使用示例

```typescript
import { VectorSearch } from '@rag-sdk/retrieval'

const vectorSearch = new VectorSearch(embeddingProvider, vectorStore)

// 基础检索
const results = await vectorSearch.retrieve('如何配置用户权限', {
  topK: 5,
  threshold: 0.7,
})

// 带元数据过滤的检索
const filteredResults = await vectorSearch.retrieve('部署指南', {
  topK: 10,
  filter: { category: '运维文档', version: 'v2.0' },
})
```

---

### 2. KeywordSearch（BM25 关键词检索）

#### 概念说明

基于 BM25 算法的关键词检索，通过词频（TF）和逆文档频率（IDF）计算查询与文档的相关性分数。这是一种经典的稀疏检索方法。

#### 解决的问题

- 专有名词、代码片段、错误码等精确匹配场景
- 向量检索对精确关键词匹配不够敏感
- 不依赖外部 Embedding 模型，可独立运行

> 源码详见：`packages/retrieval/src/search/keyword.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `topK` | `number` | `5` | 返回结果数量 |
| `k1` | `number` | `1.5` | BM25 词频饱和参数 |
| `b` | `number` | `0.75` | BM25 长度归一化参数 |

#### 使用示例

```typescript
import { KeywordSearch } from '@rag-sdk/retrieval'

const keywordSearch = new KeywordSearch(documents, { k1: 1.2, b: 0.75 })

// 精确匹配检索 — BM25 对错误信息、代码片段等精确匹配效果很好
const results = await keywordSearch.retrieve('TypeError: Cannot read property', { topK: 5 })

// 专有名词检索
const apiResults = await keywordSearch.retrieve('useCallback useMemo')
```

---

### 3. FusionSearch（融合检索）

#### 概念说明

同时使用向量检索和关键词检索，将两者的结果按权重合并。结合了向量检索的语义理解能力和关键词检索的精确匹配能力。

#### 解决的问题

- 单一检索方式各有盲区：向量检索可能漏掉精确关键词匹配，关键词检索缺乏语义理解
- 融合两种方式可以取长补短，提升整体检索质量

> 源码详见：`packages/retrieval/src/search/fusion.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `vectorWeight` | `number` | `0.5` | 向量检索权重 |
| `keywordWeight` | `number` | `0.5` | 关键词检索权重 |
| `topK` | `number` | `10` | 返回结果数量 |

#### 使用示例

```typescript
import { FusionSearch, VectorSearch, KeywordSearch } from '@rag-sdk/retrieval'

const fusion = new FusionSearch(vectorSearch, keywordSearch, {
  vectorWeight: 0.6,
  keywordWeight: 0.4,
})

// 融合检索：向量理解"内存泄漏"语义 + 关键词精确匹配"React"和"useEffect"
const results = await fusion.retrieve('React useEffect 内存泄漏', { topK: 10 })

// 偏向语义理解的场景
const semanticResults = await fusion.retrieve('如何提高系统可用性', {
  vectorWeight: 0.8,
  keywordWeight: 0.2,
})
```

### 4. RRFSearch（Reciprocal Rank Fusion，倒数排名融合）

#### 概念说明

RRF 是一种基于排名而非分数的融合算法。核心公式为 `score = Σ 1/(k + rank)`，其中 k 是常数（通常为 60）。它不依赖各路检索的原始分数（因为不同检索方式的分数尺度不同），只看每个文档在各路结果中的排名。

#### 解决的问题

- 不同检索方式的分数尺度不同（向量余弦相似度 vs BM25 分数），无法直接加权比较
- RRF 只看排名不看分数，天然解决了分数不可比的问题

> 源码详见：`packages/retrieval/src/search/rrf.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `k` | `number` | `60` | 平滑常数，控制排名对分数的影响程度 |

#### 使用示例

```typescript
import { RRFSearch, VectorSearch, KeywordSearch } from '@rag-sdk/retrieval'

const rrfSearch = new RRFSearch(vectorSearch, keywordSearch, { k: 60 })

// RRF 检索：自动处理分数尺度不同的问题
const results = await rrfSearch.retrieve('如何配置 CI/CD 流水线', { topK: 10 })
// 在两路检索中排名都靠前的文档会获得更高的 RRF 分数
```

### 5. SmallToBigSearch（小块检索大块返回）

#### 概念说明

使用较小的文档块进行检索（更精准），但返回时扩展到包含该小块的大块（更完整的上下文）。这依赖于文档分块时通过 `parentId` 建立的父子关系。

#### 解决的问题

- 小块检索精度高但上下文不完整
- 大块检索上下文完整但匹配精度低
- SmallToBig 兼顾两者：用小块精准匹配，返回大块完整上下文

> 源码详见：`packages/retrieval/src/search/small-to-big.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `topK` | `number` | `5` | 返回的大块结果数量 |

#### 使用示例

```typescript
import { SmallToBigSearch } from '@rag-sdk/retrieval'

const smallToBig = new SmallToBigSearch(vectorSearch, documentStore)

const results = await smallToBig.retrieve('用户认证流程', { topK: 3 })
// 小块精准匹配到"JWT token 验证"片段
// 返回时通过 parentId 扩展到包含完整认证流程的父 chunk
```

### 6. HierarchicalSearch（分层索引检索）

#### 概念说明

建立两层索引：摘要索引（每个文档的摘要/概述）和内容索引（文档的具体片段）。检索时先在摘要层找到相关文档，再在对应文档的内容层做精细检索。

#### 解决的问题

- 大规模文档库中，直接全量检索效率低且可能匹配到不相关文档的片段
- 分层检索先粗筛再精选，兼顾效率和精度
- 适合文档数量多、每篇文档较长的场景

> 源码详见：`packages/retrieval/src/search/hierarchical.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `summaryTopK` | `number` | `3` | 摘要层返回的文档数量 |
| `contentTopK` | `number` | `3` | 内容层每个文档返回的片段数量 |

#### 使用示例

```typescript
import { HierarchicalSearch } from '@rag-sdk/retrieval'

const hierarchical = new HierarchicalSearch(embeddingProvider, summaryIndex, contentIndex)

const results = await hierarchical.retrieve('微服务架构设计', {
  summaryTopK: 3, // 先找 3 篇相关文档
  contentTopK: 2, // 每篇文档取 2 个最相关片段
})
// 最终最多返回 3 × 2 = 6 个片段
```

## 三、后处理 (Post-Processing)

后处理是在检索完成后、送入 LLM 之前，对检索结果进行进一步优化，提升最终生成质量。所有后处理器均实现 `PostProcessor` 接口（`process(results: SearchResult[], query: string): Promise<SearchResult[]>`）。

### 1. ThresholdPostProcessor（阈值过滤）

#### 概念说明

丢弃相似度分数低于阈值的结果，确保送入 LLM 的内容都具有足够的相关性。支持固定阈值和动态阈值两种模式。

#### 解决的问题

- 检索结果中可能包含不相关的低分内容
- 低分内容会干扰 LLM 生成，引入噪声甚至导致幻觉

> 源码详见：`packages/retrieval/src/post-process/threshold.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `threshold` | `number` | `0.5` | 固定阈值 |
| `dynamic` | `boolean` | `false` | 是否启用动态阈值 |
| `stdMultiplier` | `number` | `1.0` | 动态阈值的标准差倍数 |

#### 使用示例

```typescript
import { ThresholdPostProcessor } from '@rag-sdk/retrieval'

// 固定阈值
const fixedFilter = new ThresholdPostProcessor({ threshold: 0.7 })
const filtered = await fixedFilter.process(results, query)

// 动态阈值：自动根据分数分布调整
const dynamicFilter = new ThresholdPostProcessor({ dynamic: true, stdMultiplier: 1.5 })
const dynamicFiltered = await dynamicFilter.process(results, query)
```

---

### 2. RerankerPostProcessor（重排序）

#### 概念说明

使用 Cross-Encoder 模型对 query 和每个检索结果进行联合编码，计算更精准的相关性分数，然后重新排序。Cross-Encoder 比 Bi-Encoder（Embedding 向量检索）精度更高，但计算成本也更高，因此只用于对少量结果做重排序。

#### 解决的问题

- 向量检索（Bi-Encoder）的分数不够精准
- Cross-Encoder 能捕捉 query 和文档之间更细粒度的交互关系
- 在大量候选结果中筛选出真正最相关的 top 结果

> 源码详见：`packages/retrieval/src/post-process/reranker.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `topK` | `number` | `5` | 重排序后保留的结果数量 |
| `model` | `string` | 内置默认 | Reranker 模型名称 |

#### 使用示例

```typescript
import { RerankerPostProcessor } from '@rag-sdk/retrieval'

const reranker = new RerankerPostProcessor(rerankerScorer, { topK: 5 })

// 先用向量检索获取候选结果
const candidates = await vectorSearch.retrieve(query, { topK: 20 })

// 用 Reranker 重排序，取 top 5
const reranked = await reranker.process(candidates, query)
// Reranker 能更准确地判断哪些结果真正与 query 相关
```

---

### 3. ContextEnrichPostProcessor（上下文增强）

#### 概念说明

检索到某个文档片段后，自动带上其前后相邻的片段，提供更完整的上下文信息。

#### 解决的问题

- 检索到的 chunk 可能缺少前后文，信息不完整
- 一个段落的关键信息可能在相邻段落中有补充说明
- LLM 需要更完整的上下文才能生成准确的回答

> 源码详见：`packages/retrieval/src/post-process/context-enrich.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `window` | `number` | `1` | 前后各扩展的 chunk 数量 |

#### 使用示例

```typescript
import { ContextEnrichPostProcessor } from '@rag-sdk/retrieval'

const enricher = new ContextEnrichPostProcessor(chunkStore, { window: 2 })

const results = await vectorSearch.retrieve(query, { topK: 5 })
const enriched = await enricher.process(results, query)
// 原始结果: chunk-5
// 增强后: chunk-3 + chunk-4 + chunk-5 + chunk-6 + chunk-7
// LLM 获得了更完整的前后文上下文
```

---

### 4. SelectiveContextPostProcessor（选择性上下文）

#### 概念说明

在检索到的 chunk 中，只保留与 query 相关的句子，过滤掉不相关的句子。这是一种细粒度的上下文过滤，在句子级别操作。

#### 解决的问题

- 一个 chunk 中可能只有部分句子与 query 相关
- 不相关的句子会占用上下文窗口、干扰 LLM 生成
- 精简上下文可以提升生成质量并降低成本

> 源码详见：`packages/retrieval/src/post-process/selective-context.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `threshold` | `number` | `0.5` | 句子相关性阈值 |

#### 使用示例

```typescript
import { SelectiveContextPostProcessor } from '@rag-sdk/retrieval'

const selectiveCtx = new SelectiveContextPostProcessor(embeddingProvider, { threshold: 0.6 })

const results = await vectorSearch.retrieve(query, { topK: 5 })
const filtered = await selectiveCtx.process(results, query)

// 原始 chunk 包含 React 和 Vue 相关内容
// query: "React 性能优化"
// 过滤后: 只保留与 React 相关的句子，去掉 Vue 相关内容
```

---

### 5. CompressionPostProcessor（上下文压缩）

#### 概念说明

使用轻量级 LLM 对检索到的内容进行压缩，去掉与 query 不相关的部分，保留核心信息。与 `SelectiveContextPostProcessor` 不同，`CompressionPostProcessor` 不是简单过滤句子，而是理解内容后进行智能摘要和压缩。

#### 解决的问题

- 检索到的内容可能很长，超出 LLM 上下文窗口限制
- 大量不相关内容会浪费 token、增加成本
- 压缩后的内容更聚焦，有助于提升生成质量

> 源码详见：`packages/retrieval/src/post-process/compression.ts`

#### 关键参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `targetTokens` | `number` | `500` | 压缩后的目标 token 数量 |
| `compressPrompt` | `string` | 内置默认模板 | 压缩提示词模板 |

#### 使用示例

```typescript
import { CompressionPostProcessor } from '@rag-sdk/retrieval'

const compressor = new CompressionPostProcessor(llmProvider, { targetTokens: 300 })

const results = await vectorSearch.retrieve(query, { topK: 5 })
const compressed = await compressor.process(results, query)

// 原始内容 2000 tokens → 压缩后 300 tokens
// 保留了与 query 相关的核心信息，去掉了无关内容
```

## 模块组合使用

检索模块的各个组件可以灵活组合，构建适合不同场景的检索管道。所有组件都实现标准接口，可任意替换：

```typescript
import {
  QueryRewriter,
  VectorSearch,
  KeywordSearch,
  RRFSearch,
  ThresholdPostProcessor,
  RerankerPostProcessor,
  ContextEnrichPostProcessor,
} from '@rag-sdk/retrieval'

/**
 * 完整的检索管道示例：查询变换 → 多路检索 → 融合 → 过滤 → 重排序 → 上下文增强
 */
async function buildRetrievalPipeline(query: string) {
  // 1. 查询变换：改写模糊查询
  const rewriter = new QueryRewriter(llm)
  const rewritten = await rewriter.transform(query)

  // 2. 多路并行检索
  const [vectorResults, keywordResults] = await Promise.all([
    vectorSearch.retrieve(rewritten, { topK: 20 }),
    keywordSearch.retrieve(rewritten, { topK: 20 }),
  ])

  // 3. RRF 融合（不依赖分数尺度）
  const rrfSearch = new RRFSearch(vectorSearch, keywordSearch)
  const fused = await rrfSearch.retrieve(rewritten, { topK: 20 })

  // 4. 阈值过滤：去除低相关度结果
  const filter = new ThresholdPostProcessor({ threshold: 0.5 })
  const filtered = await filter.process(fused, query)

  // 5. 重排序：用 Cross-Encoder 精排
  const reranker = new RerankerPostProcessor(scorer, { topK: 10 })
  const reranked = await reranker.process(filtered, query)

  // 6. 上下文增强：补充相邻 chunk
  const enricher = new ContextEnrichPostProcessor(chunkStore, { window: 1 })
  const enriched = await enricher.process(reranked, query)

  return enriched
}
```
