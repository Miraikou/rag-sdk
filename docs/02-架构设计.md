### 2.2 依赖关系表

| 包名 | 依赖的内部包 | 说明 |
|------|-------------|------|
| `@rag-sdk/core` | 无 | 核心类型定义和 Pipeline 引擎，零运行时依赖 |
| `@rag-sdk/llm` | `core` | LLM 抽象接口和各提供商适配器 |
| `@rag-sdk/embedding` | `core` | 嵌入模型抽象接口和适配器 |
| `@rag-sdk/storage` | `core` | 向量存储抽象接口和适配器 |
| `@rag-sdk/document` | `core`, `embedding` | 文档加载、切块、清洗（语义切块需要 embedding） |
| `@rag-sdk/retrieval` | `core`, `embedding`, `storage` | 检索策略（需要向量计算和存储查询） |
| `@rag-sdk/generation` | `core`, `llm` | 生成策略（需要 LLM 调用） |
| `@rag-sdk/evaluation` | `core`, `llm` | 评测指标和数据集管理（部分指标需要 LLM 评判） |
| `@rag-sdk/knowledge-graph` | `core`, `llm`, `storage` | 知识图谱（实体抽取需要 LLM，图存储需要存储抽象） |
| `rag-sdk` | 所有子包 | 主包，re-export 所有子包的公共 API |

### 2.3 设计原则

- **无循环依赖**：依赖关系形成严格的有向无环图（DAG）
- **core 零依赖**：core 包不依赖任何其他包，确保稳定性
- **adapter 可选**：storage、llm 等包中的具体 adapter 按需安装 peer dependency
- **接口隔离**：跨包通信只通过 core 中定义的接口和类型

## 3. Pipeline 编排设计

### 3.1 RAGPipeline 核心入口

`RAGPipeline` 是整个 SDK 的核心入口，负责编排从文档导入到答案生成的完整流程。

```ts
interface RAGPipelineConfig {
  // 必需组件
  llm: LLM;
  embedding: EmbeddingModel;
  store: VectorStore;

  // 可选组件（提供默认实现）
  chunker?: Chunker;                    // 默认 RecursiveChunker
  retriever?: Retriever;                // 默认 VectorRetriever
  postProcessors?: PostProcessor[];     // 默认为空
  generator?: Generator;                // 默认 GroundingGenerator
  queryTransformer?: QueryTransformer;  // 默认为空（不转换）

  // 可选的高级组件
  graphStore?: GraphStore;              // 知识图谱存储
  loaders?: DocumentLoader[];           // 文档加载器

  // 配置
  hooks?: PipelineHooks;                // 生命周期钩子
}
```

### 3.2 Pipeline 阶段划分

Pipeline 分为两个主要流程：**导入流程（Ingestion）** 和 **查询流程（Query）**。

#### 导入流程（Ingestion Pipeline）

```
文档输入 → 文档加载 → 文档清洗 → 文档切块 → Embedding → 向量存储
              ↓           ↓          ↓          ↓          ↓
          Loader     Cleaner    Chunker    Embedding   VectorStore
```

```ts
// 导入流程的 Stage 定义
class IngestionStage implements PipelineStage<RawDocument[], void> {
  async execute(
    input: RawDocument[],
    context: PipelineContext,
  ): Promise<void> {
    const loaded = await this.loadDocuments(input);
    const cleaned = await this.cleanDocuments(loaded);
    const chunks = await this.chunkDocuments(cleaned);
    const embeddings = await this.embedChunks(chunks);
    await this.storeVectors(embeddings);
  }
}
```

#### 查询流程（Query Pipeline）

```
用户查询 → Query Transform → 检索 → 后处理 → Prompt 构建 → LLM 生成 → 答案后处理
              ↓               ↓        ↓          ↓            ↓           ↓
         QueryTransformer Retriever  PostProc   Template     LLM        Formatter
```

```ts
// 查询流程的 Stage 定义
class QueryStage implements PipelineStage<Query, QueryResult> {
  async execute(
    input: Query,
    context: PipelineContext,
  ): Promise<QueryResult> {
    const transformedQuery = await this.transformQuery(input);
    const retrieved = await this.retrieve(transformedQuery);
    const processed = await this.postProcess(retrieved);
    const prompt = await this.buildPrompt(processed, input);
    const answer = await this.generate(prompt);
    return this.formatResult(answer, processed);
  }
}
```

### 3.3 中间件 / Hooks 系统

Pipeline 支持在每个阶段前后插入自定义逻辑：

```ts
interface PipelineHooks {
  // 导入流程钩子
  beforeIngest?: (docs: RawDocument[]) => RawDocument[] | Promise<RawDocument[]>;
  afterIngest?: (chunks: Chunk[]) => void | Promise<void>;

  // 查询流程钩子
  beforeQuery?: (query: Query) => Query | Promise<Query>;
  afterRetrieve?: (results: RetrievedChunk[]) => RetrievedChunk[] | Promise<RetrievedChunk[]>;
  beforeGenerate?: (prompt: string, context: RetrievedChunk[]) => string | Promise<string>;
  afterGenerate?: (result: QueryResult) => QueryResult | Promise<QueryResult>;

  // 全局钩子
  onError?: (error: Error, stage: string, context: PipelineContext) => void;
  onProgress?: (event: ProgressEvent) => void;
}
```

使用示例：

```ts
const rag = new RAGPipeline({
  // ... 其他配置
  hooks: {
    // 查询前自动添加时间上下文
    beforeQuery: (query) => ({
      ...query,
      text: `[当前时间: ${new Date().toISOString()}] ${query.text}`,
    }),

    // 检索后过滤低分结果
    afterRetrieve: (results) =>
      results.filter((r) => r.score > 0.7),

    // 全局错误处理
    onError: (error, stage) => {
      logger.error(`Pipeline stage "${stage}" failed:`, error);
    },

    // 进度通知
    onProgress: (event) => {
      console.log(`[${event.stage}] ${event.message} (${event.progress}%)`);
    },
  },
});
```

### 4.2 数据流中的类型流转

```
// 导入流程数据类型流转
RawDocument[]
  → CleanedDocument[]     （清洗后）
    → Chunk[]             （切块后，携带 parentDoc 和 position 元数据）
      → EmbeddedChunk[]   （添加 embedding 向量后）
        → 存入 VectorStore

// 查询流程数据类型流转
Query { text: string, filters?: MetadataFilter }
  → TransformedQuery { queries: string[], embedding?: number[] }
    → RetrievedChunk[] { chunk: Chunk, score: number, source: string }
      → ProcessedChunk[] { chunk: Chunk, score: number, rerankScore?: number }
        → QueryResult { answer: string, sources: Source[], confidence: number }
```

## 5. 实施阶段

### Phase 1：基础骨架（预计 2 周）

**目标**：搭建项目基础结构，实现最小可用的 RAG pipeline。

| 任务 | 详情 |
|------|------|
| 项目初始化 | 搭建 Monorepo 结构，配置 pnpm workspace、Turborepo、tsup、vitest、eslint、prettier |
| 核心类型定义 | 定义 `Document`、`Chunk`、`Embedding`、`Query`、`QueryResult`、`VectorStore`、`LLM`、`EmbeddingModel` 等核心接口 |
| Pipeline 引擎 | 实现 `RAGPipeline` 基础编排，支持串联 Stage 和 Hooks |
| OpenAI LLM Adapter | 实现 OpenAI GPT-3.5/4 的 generate 和 stream 方法 |
| OpenAI Embedding Adapter | 实现 text-embedding-3-small/large 适配器 |
| MemoryStore | 实现内存向量存储，支持余弦相似度搜索 |
| 基础 Pipeline | 串联：文档输入 → 简单切块 → Embedding → 存储 → 向量检索 → 基础生成 |

**里程碑**：能通过 `rag.ingest()` 导入文档，通过 `rag.query()` 获取基于文档的回答。

### Phase 2：检索增强（预计 2 周）

**目标**：提升检索质量，提供多种检索策略。

| 任务 | 详情 |
|------|------|
| 递归切块器 | `RecursiveChunker`：按分隔符层级递归切块，支持自定义分隔符列表 |
| 语义切块器 | `SemanticChunker`：基于 embedding 相似度进行智能语义分段 |
| Query 变换 | `HyDEQueryTransformer`（假设文档嵌入）、`MultiQueryTransformer`（多查询扩展）、`QueryRewriter`（查询重写） |
| 混合检索 | `FusionRetriever`：支持加权融合、RRF（Reciprocal Rank Fusion）等策略 |
| 重排序 | `Reranker`：基于交叉编码器或 LLM 的结果重排序 |
| 冗余过滤 | `RedundancyFilter`：移除高度重复的检索结果 |
| MMR 检索 | `MMRRetriever`：Maximal Marginal Relevance 多样性检索 |

**里程碑**：支持至少 3 种切块策略 + 3 种检索策略 + 2 种后处理策略。

### Phase 3：生成增强（预计 2 周）

**目标**：提升生成质量，支持引用溯源和自反思。

| 任务 | 详情 |
|------|------|
| Prompt Template | 模板引擎：支持变量注入 `{{variable}}`、条件渲染 `{#if}...{/if}`、循环 `{#each}...{/each}` |
| Grounding 生成 | `GroundingGenerator`：基于检索结果约束生成，减少幻觉 |
| Citation 生成 | `CitationGenerator`：答案中标注引用来源，支持多种引用格式 |
| Self-RAG | `SelfRAGGenerator`：生成时自反思，判断答案质量和是否需要额外检索 |
| 流式生成 | 所有 Generator 支持 `AsyncIterable<string>` 流式输出 |

**里程碑**：生成的答案包含来源引用，支持流式输出。

### Phase 4：文档处理增强（预计 1.5 周）

**目标**：丰富文档处理能力，支持多种格式和增量更新。

| 任务 | 详情 |
|------|------|
| 文档加载器 | `TextLoader`、`PDFLoader`（基于 pdf-parse）、`HTMLLoader`（基于 cheerio）、`URLLoader` |
| Markdown 切块器 | `MarkdownChunker`：按标题层级（h1-h6）智能切块 |
| 文档去重 | `Deduplicator`：基于内容哈希（SHA-256）和 MinHash 的近似去重 |
| 文档清洗 | `DocumentCleaner`：去除页眉页脚、特殊字符、重复段落 |
| 元数据提取 | `MetadataExtractor`：自动提取标题、关键词、摘要 |
| 文档增强 | `ContextEnhancer`：为每个切块添加上下文（父文档摘要、相邻切块） |
| 增量更新 | `IncrementalUpdater`：基于文档哈希判断变更，仅处理新增/修改的文档 |

**里程碑**：支持 PDF/HTML/Markdown 加载，支持增量更新。

### Phase 5：知识图谱（预计 2 周）

**目标**：实现基于知识图谱的增强检索。

| 任务 | 详情 |
|------|------|
| 实体抽取 | `EntityExtractor`：基于 LLM 的命名实体识别（NER），支持 few-shot 定制 |
| 关系抽取 | `RelationExtractor`：从文本中提取实体间的关系（三元组） |
| 内存图存储 | `MemoryGraphStore`：基于 Map 的内存图数据结构，支持节点/边的 CRUD |
| Neo4j Adapter | `Neo4jGraphStore`：Neo4j 图数据库适配器 |
| 图检索 | `GraphRetriever`：基于图遍历的关联检索（BFS/DFS），支持深度限制 |
| 图增强 RAG | `GraphEnhancedRetriever`：融合向量检索和图检索的结果 |

**里程碑**：能通过知识图谱回答实体关系类问题。

### Phase 6：评测模块（预计 1.5 周）

**目标**：提供完整的 RAG 评测框架。

| 任务 | 详情 |
|------|------|
| 检索指标 | `Recall@K`、`Precision@K`、`MRR`（Mean Reciprocal Rank）、`NDCG`（Normalized Discounted Cumulative Gain） |
| 生成指标 | `FaithfulnessEvaluator`（忠实度）、`RelevanceEvaluator`（相关性）、`CoherenceEvaluator`（连贯性） |
| 端到端评测 | `E2EEvaluator`：完整 pipeline 的准确率、F1 评测 |
| 数据集管理 | `DatasetLoader`：加载评测数据集（JSON/CSV 格式），支持 train/test 划分 |
| 评测报告 | `ReportGenerator`：生成包含指标、图表的评测报告（Markdown / JSON 格式） |
| A/B 对比 | `ComparisonRunner`：多策略并行评测，生成对比表格 |

**里程碑**：能对不同切块/检索/生成策略进行量化对比。

### Phase 7：路由与高级功能（预计 1 周）

**目标**：提供智能路由、预设 Pipeline 和流式输出等高级功能。

| 任务 | 详情 |
|------|------|
| 检索路由 | `RetrievalRouter`：根据查询类型（事实类、分析类、创意类）自动选择最优检索策略 |
| 预设 Pipeline | `SimpleRAG`、`AdvancedRAG`、`GraphRAG` 等预配置 Pipeline，一行代码即可使用 |
| 流式输出 | 完整的 SSE 流式输出支持，包括前端集成示例 |
| 上下文压缩 | `ContextCompressor`：LLM 驱动的上下文压缩，仅保留与查询相关的信息 |
| 令牌预算管理 | `TokenBudgetManager`：自动管理 prompt 中的 token 分配 |
| 性能监控 | Pipeline 各阶段的耗时统计和性能报告 |

**里程碑**：发布 v1.0.0，包含完整的文档站和示例项目。

### 7.3 配置说明

| 配置项 | 说明 |
|--------|------|
| `dependsOn: ["^build"]` | 构建当前包前，先构建其依赖的内部包（拓扑排序） |
| `inputs` | 影响缓存键的文件列表，只有这些文件变化时才重新执行 |
| `outputs` | 构建产物目录，用于缓存恢复 |
| `cache: true` | 启用远程/本地缓存，未变更时跳过执行 |
| `persistent: true` | 标记为长期运行任务（如 dev server），不会被其他任务等待 |

### 8.3 各子包独立发布策略

#### 版本管理

使用 [Changesets](https://github.com/changesets/changesets) 管理版本和 CHANGELOG：

```bash
# 开发者在提交 PR 时创建 changeset
pnpm changeset

# CI 自动根据 changeset 计算版本号并发布
pnpm release
```

#### 发布流程

```
1. 开发者提交代码 + changeset 文件（.changeset/*.md）
   ↓
2. CI 运行测试（vitest）+ lint（eslint）+ 类型检查（tsc）
   ↓
3. 合并到 main 分支时，CI 检测 changeset
   ↓
4. Release PR 自动创建，包含版本升级和 CHANGELOG
   ↓
5. 维护者审核后合并 Release PR
   ↓
6. 自动发布到 npm（各子包独立版本号）
```

#### 包发布顺序

由于内部包存在依赖关系，Turborepo 会自动按拓扑排序决定发布顺序：

```
1. @rag-sdk/core           （无依赖，最先发布）
2. @rag-sdk/llm            （依赖 core）
   @rag-sdk/embedding      （依赖 core，可与 llm 并行）
   @rag-sdk/storage        （依赖 core，可与 llm 并行）
3. @rag-sdk/document       （依赖 core + embedding）
   @rag-sdk/retrieval      （依赖 core + embedding + storage）
   @rag-sdk/generation     （依赖 core + llm）
   @rag-sdk/evaluation     （依赖 core + llm）
4. @rag-sdk/knowledge-graph（依赖 core + llm + storage）
5. rag-sdk                 （依赖所有子包，最后发布）
```

#### 用户安装方式

```bash
# 方式一：安装主包（包含所有功能）
npm install rag-sdk

# 方式二：按需安装子包（减小包体积）
npm install @rag-sdk/core @rag-sdk/llm @rag-sdk/storage @rag-sdk/retrieval @rag-sdk/generation

# 安装特定 adapter
npm install openai              # OpenAI LLM/Embedding
npm install chromadb            # ChromaDB 向量存储
```
